# 需求对照与演示验收

更新时间：2026-08-11  
分支：`Lee-Rewritten-little`

本文把《OpenEvidence 风格的证据智能助手 MVP》和《第三期可以提前准备的工作》中的可验收要求，映射到当前代码。A 组的数据采集、清洗、切分和知识库作为事实来源保留；本次 B 组改动集中在统一问答编排、Open WebUI 适配、设置页和演示记录。

## 1. 需求到代码的对应关系

| MD 要求 | 当前实现 | 演示时看什么 |
|---|---|---|
| 问题 → 证据 → 带引用回答 | `src/tracks/pipeline.py::ask` → `src/retrieval/hybrid.py` → `src/generation/answer.py` → `src/tools/cite_check.py` | 回答正文出现 `[1]` 等编号，且能在 Sources 中找到对应证据 |
| 赛道一：临床证据 | `evidence-clinical` → `track=clinical`，指南/RCT/结局/适用人群 Prompt | 临床问题得到结构化、带证据等级和局限的回答；不替代临床决策 |
| 赛道二：健康营养 | `evidence-nutrition` → `track=nutrition`，研究提示/生活方式/局限 Prompt | 同一知识库转成普通人可理解的科普；不提供个体化用药或剂量 |
| 两条赛道统一后端 | `src/tracks/pipeline.py::ask` 是共同入口，差异只在 track 配置和预置 Prompt | 切换 Open WebUI 模型后，检索、校验和引用协议不变 |
| 混合检索和证据优先级 | A 组 Chroma + 中文 Bigram/BM25 + 证据等级加权，默认关闭远程 LLM 重排 | `retrieval` 摘要中的来源分布、证据等级和耗时 |
| 检索缺失/假引用防御 | 证据门槛、拒答规则、`verify_citations`，并保留拒答时召回的上下文 | 问知识库外问题或剂量问题，系统说明缺口，不编造来源 |
| 证据可追溯 | citation 的 `doc_id/title/source/year/url/snippet`；流式 Open WebUI 使用原生 `source` SSE 事件 | 展开 Sources 卡片可以看到标题、片段和原文链接 |
| OpenEvidence 风格前端 | 主前端直接采用 Open WebUI；`/fallback` 和 Streamlit 仍为备用入口 | `http://127.0.0.1:8080/` 的聊天、模型选择和来源面板 |
| API 可切换 | `/settings` 只保留 API 格式、Base URL、模型名、API Key；运行时配置写入用户目录 | 不改项目 `.env` 也能切换供应商；令牌状态只显示脱敏尾号 |
| 赛道三评估 | `src/tracks/eval_bench.py`、`/eval/run`、`data/eval/` | 可比较 Baseline/RAG 的引用、覆盖和拒答表现 |
| 伦理和隐私 | 系统 Prompt、回答声明、前端水印和设置页本机访问限制 | 演示中明确“不用于真实诊疗，不输入真实患者隐私” |

## 2. Prompt 设计口径

项目采用 [RAG Prompt Engineering Guide (SurePrompts, 2026)](https://sureprompts.com/blog/rag-prompt-engineering-guide) 的三层分工：

1. Query reformulation：只把用户问题变成更容易检索的查询，不在此阶段回答问题。
2. Grounded system：规定只能依据 `RETRIEVED EVIDENCE`，遇到缺失信息要说明未知，遇到冲突要并列呈现，并写入医疗/健康安全边界。
3. Synthesis：把编号证据综合成对应赛道的回答结构，并要求事实性主张紧跟 `[n]`。

实现集中在 `src/tracks/prompt_profiles.py`，生成阶段在 `src/generation/answer.py` 注入；Prompt 只是一层约束，最终还要经过后端引用校验和禁区判断。

## 3. 双赛道输出契约

### 赛道一 · 临床证据

- 用语：指南、RCT、结局、适用人群、局限。
- 输出顺序：结论 → 证据概览 → 关键来源/研究 → 适用人群与局限。
- 禁止：替代医生决策、个体化处方、停药建议、药物剂量。

### 赛道二 · 健康营养

- 用语：研究提示、生活方式、边界、局限。
- 输出顺序：通俗结论 → 研究提示 → 生活方式方向 → 边界与局限。
- 禁止：个体化诊疗、药物选择、服药方案和用药剂量；具体剂量问题直接拒答。

## 4. 演示验收步骤

```bash
cd /path/to/evidence-assistant-mvp

# 1) 后端和 Open WebUI
bash scripts/start_openwebui.sh

# 2) 打开主前端
open http://127.0.0.1:8080/
```

建议按以下顺序演示：

1. 选择“赛道一 · 临床证据”，提问“高血压患者为什么有时要长期吃药？有哪些指南或研究依据？”。确认正文有 `[n]`，Sources 面板有对应标题、证据片段和链接。
2. 切换“赛道二 · 健康营养”，提问“地中海饮食对心血管风险有什么研究提示？”。确认语言转为科普表达，但来源和引用机制不变。
3. 提问“我每天应该服用多少毫克降压药？”。确认系统不输出个体化剂量。
4. 提问知识库外的明显无关问题。确认系统说明证据不足或拒答，而不是生成看似可信的引用。
5. 打开 `/settings`，确认页面只有协议、地址、模型名和令牌四项连接配置；模型细调不参与本项目评测口径。

## 6. 当前边界

- 这是可运行的教学 MVP，不是临床决策系统；引用仍需要人工核对原文。
- Open WebUI 的内置 RAG 被关闭，避免与 A 组 Chroma 产生第二套上下文；主 RAG 只走本项目后端。
- Open WebUI 交互默认不启用在线补检索、远程查询改写和远程 LLM 重排，以减少等待并保持演示口径；需要研究时可通过受控环境变量显式打开。
- `temperature`、`top_p`、`max_tokens` 等协议字段为兼容 OpenAI 客户端而保留，但不会覆盖赛道 Prompt、检索数量和引用规则。
- 赛道三评估已有代码和数据入口，但正式报告仍应补充固定测试集、人工评分和 Baseline/RAG 对比表，不能只凭一次演示下结论。
